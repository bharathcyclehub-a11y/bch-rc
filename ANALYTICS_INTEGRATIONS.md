# Admin Analytics reporting connections

Storefront tracking tags do not authorize the backend to read provider reports. The admin Analytics integrations have explicit setup, connected, wrong-storefront and provider-error states. Missing data is never shown as a verified zero.

## Server configuration

Configure these on the deployment; never give private values a `NEXT_PUBLIC_` prefix or commit credentials:

| Variable | Purpose |
| --- | --- |
| `ANALYTICS_INTEGRATION_SITE_ID` | Existing database storefront ID whose reports these credentials represent; e.g. `prc`. The admin must have access to it. |
| `GA4_PROPERTY_ID` | Numeric GA4 property ID. This differs from the public `G-…` measurement ID. |
| `GA4_CLIENT_EMAIL` | Google service-account email granted Viewer access to that GA4 property. |
| `GA4_PRIVATE_KEY` | Corresponding service-account PEM private key. Literal `\n` line separators are accepted. |
| `GA4_HOSTNAME` | Storefront hostname, e.g. `pocketrccars.com`. Reports filter to this hostname and its `www` variant. |
| `CLARITY_EXPORT_API_TOKEN` | Token generated by the correct Clarity project's admin under Settings → Data Export. |
| `NEXT_PUBLIC_CLARITY_ID` | Existing public Clarity project ID; must match the project that issued the export token. |
| `CRON_SECRET` | Existing scheduler secret; required for the archive endpoint. |

Enable the Google Analytics Data API in the Google Cloud project and grant the service account access in GA4 Admin → Property access management. No domain-wide delegation or customer Google login is required. The backend uses the read-only Analytics OAuth scope, a signed service-account assertion and short-lived OAuth access tokens. Credentials and raw provider errors never enter client props.

The connection represents one mapped storefront. A multi-store admin sees that source explicitly labeled, while admins without the mapped storefront cannot retrieve its report. Clarity's export response does not identify its project, so verify the token/project mapping in Clarity during setup. It is not possible to validate a wrong-project token from the documented export response.

## Dates, totals and refresh

GA4 reads the selected inclusive calendar dates, including periods beyond 90 days, according to the property's time zone. Set that time zone to Asia/Kolkata for alignment with the order ledger. Reports show the returned time zone and preserve privacy threshold/sampling warnings. The data API can only return history Google actually collected. Total users come from an aggregate query; channel user counts are never added together. GA4 purchase events are a separate source from verified orders and may differ due to consent, blockers, processing or event implementation.

GA4 results refresh about every 15 minutes using Next's Data Cache. Clarity's recent snapshot refreshes about every six hours, independent of the sales date selector; its error states are cached too. The normal budget is roughly four recent snapshots and one successful archive fetch per day. Cache eviction, deployment cache resets, other API users, or concurrent cold starts can still consume additional calls; provider quota errors remain visible and automatic retries are limited by the cache interval. Do not manually refresh/clear the cache repeatedly.

## Clarity history setup and limitations

Microsoft currently limits its export API to the previous rolling 24, 48 or 72 hours, ten requests per project per day and 1,000 response rows without pagination. It does not export recordings or arbitrary historical dates. The live panel therefore always identifies its last-72-hour window, independently of the sales filter.

Apply `src/db/migrations/manual/2026-09-11_clarity_snapshots.sql` explicitly with the repository's manual migration runner, after reviewing it:

```sh
npx tsx --env-file=.env.local scripts/apply-manual-migration.ts src/db/migrations/manual/2026-09-11_clarity_snapshots.sql
```

This migration is intentionally outside Drizzle's migration journal, matching the repository's other manual migrations. `npm run db:migrate` will not apply it. It creates an aggregate snapshot table and a durable attempt state table, both with RLS enabled and no public policies. No raw customer data, page URLs, recordings, or API tokens are stored.

For longer first-party date ranges, also apply the independent reporting-index migration supplied in this change:

```sh
npx tsx --env-file=.env.local scripts/apply-manual-migration.ts src/db/migrations/manual/2026-09-11_analytics_indexes.sql
```

Review both files against the deployment database before running them. Neither migration was applied as part of the local implementation work.

The `/api/cron/analytics-snapshots` endpoint is scheduled hourly at minute ten in `vercel.json`. It requires the exact `Authorization: Bearer <CRON_SECRET>` header. The collector checks for a due snapshot before contacting Microsoft: it saves approximately one rolling 24-hour snapshot per day, allowing up to one minute of scheduler drift so a millisecond timing difference does not skip a day. Failed provider requests wait at least six hours before retrying. A PostgreSQL transaction advisory lock prevents simultaneous archive collectors. Saved snapshots are retained without a 90-day cutoff.

Scheduler timing can leave small overlaps or gaps between rolling windows; these are documented in the snapshot notes. These are observations of actual rolling periods, not reconstructed IST calendar-day totals. The history date selector includes snapshots whose window ends within the selected IST dates. The panel exposes the first saved time and actual windows; it never sums snapshot counts or unique users, averages percentages, or silently imputes missing days. At most the latest 400 matching snapshots are displayed, with the full matching count and an explicit truncation note.

No archive predates the first successful scheduled collection. Existing Clarity recordings cannot be backfilled through this API. Sales history and GA4 reports remain available separately according to their underlying retained data. If the migration is absent, the admin displays the missing-storage state while other Analytics sections still work.

## Verification

`node --import tsx scripts/verify-analytics-integrations.ts` exercises offline provider fixtures: historical/single-day range validation, distinct-user totals, reordered GA4 headers, empty versus malformed reports, privacy threshold notes, rolling Clarity windows, collector scheduling drift/retry throttling, and suppression of URL-containing or ambiguous grouped responses. It does not prove a live provider connection.

After setting credentials, open Admin → Analytics and confirm the GA4 and Clarity panels show a received report and fetch timestamp. Compare a date range against the source dashboards and the first-party ledger, accounting for provider time zones/consent. After applying the migration and enabling the schedule, verify that a saved 24-hour snapshot appears in Analytics and review its actual window and any overlap/gap notes.
